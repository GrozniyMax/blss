# Роли и права доступа

Этот документ описывает систему управления доступом на основе ролей (RBAC), реализованную в приложении BLSS.

## Обзор

Система использует **Spring Security** с **методным уровнем безопасности** (аннотации `@PreAuthorize`) для контроля доступа к API-эндпоинтам. Пользователи аутентифицируются через HTTP Basic Authentication с учётными данными, хранящимися в XML-файле (`users.xml`).

## Доступные роли

| Роль | Описание |
|------|----------|
| `ADMIN` | Администратор системы с полным доступом ко всем эндпоинтам |
| `MANAGER` | Менеджер — управление заказами и пунктами выдачи |
| `CONSULTANT` | Операционный сотрудник — просмотр и управление статусами заказов |
| `WAREHOUSE` | Сотрудник склада — выдача товаров |
| `USER` | Клиент — создание и просмотр собственных заказов |

## Пользователи по умолчанию (для разработки)

| Имя пользователя | Пароль | Роли |
|------------------|--------|------|
| `admin` | `admin123` | `ADMIN` |
| `manager` | `manager123` | `MANAGER` |
| `consultant` | `consultant123` | `CONSULTANT` |
| `warehouse` | `warehouse123` | `WAREHOUSE` |
| `senior_consultant` | `senior123` | `CONSULTANT`, `WAREHOUSE` |

> ⚠️ **Предупреждение по безопасности**: Измените пароли по умолчанию в production!

## Права доступа по ролям

### 🔴 ADMIN

**Полный доступ к системе** — может обращаться ко всем эндпоинтам.

| Эндпоинт | Метод | Описание |
|----------|-------|----------|
| `/users` | POST | Создать нового пользователя |
| `/users` | GET | Получить список всех пользователей |
| `/users/{username}` | GET | Получить данные пользователя |
| `/users/{username}` | PATCH | Обновить пользователя (пароль, роли, статус) |
| `/users/{username}` | DELETE | Удалить пользователя |
| `/delivery-points` | POST | Создать пункт выдачи |
| `/inventory/products` | POST | Создать товар |
| `/inventory/products/{id}` | PUT | Обновить товар |
| `/inventory/products/{id}/count` | PATCH | Изменить количество на складе |
| `/inventory/products/{id}` | GET | Получить информацию о товаре |
| `/inventory/products` | GET | Получить список всех товаров |
| `/inventory/products/{id}/count` | GET | Получить количество товара |
| `/order/create` | POST | Создать заказ (с проверкой безопасности) |
| `/order/{id}` | GET | Получить информацию о заказе (с проверкой безопасности) |
| `/order/{id}/status/next` | PATCH | Перевести заказ на следующий статус |
| `/order/{id}/status/cancel` | PATCH | Отменить заказ |
| `/mark-delivered` | POST | Отметить товар заказа как доставленный |

**Клиент** — может создавать заказы и просматривать только собственные заказы.

|----------|-------|----------|

- Отметка доставки (`/mark-delivered`)

## Специальные правила доступа

### Сервис безопасности заказов

Некоторые эндпоинты заказов используют пользовательские проверки безопасности через `OrderSecurityService`:

1. **Создание заказа** (`/order/create`):
   - Используется: `@orderSecurityService.canCreateOrderFor(#order.owner())`
   - Проверяет, что аутентифицированный пользователь может создавать заказы для указанного владельца
   - **USER** может создавать заказы только для себя

2. **Получение заказа** (`/order/{id}`):
   - Используется: `@orderSecurityService.canAccessOrder(#id, authentication.name)`
   - Проверяет, что у пользователя есть доступ к конкретному заказу
   - **USER** может просматривать только свои заказы

## Иерархия ролей

```
ADMIN (полный доступ)
  │
  ├── MANAGER (операции + пункты выдачи + запасы)
  │     │
  │     └── CONSULTANT (управление статусами заказов)
  │
  ├── WAREHOUSE (выдача товаров)
  │
  └── USER (клиент — только свои заказы)
```

**Примечание:** USER не входит в иерархию сотрудников — это роль клиента. Пользователи могут иметь несколько ролей (например, `senior_consultant`: CONSULTANT + WAREHOUSE).

## Детали реализации

### Конфигурация безопасности

- **Аутентификация**: HTTP Basic Auth
- **Авторизация**: Методный уровень безопасности с `@PreAuthorize` + URL-based правила в `SecurityConfig`
- **Хранилище пользователей**: XML-файл (`users.xml`)
- **Хранение паролей**: В открытом виде (только для разработки)

### Ключевые классы безопасности

- `SecurityConfig` — конфигурация Spring Security (URL-based правила)
- `OrderSecurityService` — пользовательская проверка доступа к заказам
- `XmlUserRepository` — XML-хранилище пользователей

### Добавление новых ролей

1. Определить роль в `users.xml` для пользователей
2. Добавить `@PreAuthorize("hasRole('NEW_ROLE')")` или `@PreAuthorize("hasAnyRole('ROLE1', 'NEW_ROLE')")` к методам контроллера
3. При необходимости добавить URL-based правила в `SecurityConfig`
4. Обновить эту документацию

## Рабочий процесс статусов заказа

Роли, которые могут переводить заказ на следующий статус (`CONSULTANT`, `MANAGER`, `ADMIN`):

```
CREATED → PROCESSING → IN_DELIVERY → READY_FOR_PICKUP → DONE
                                 ↓
                            CANCELED
```

**Описание статусов:**
- `CREATED` — Заказ создан
- `PROCESSING` — Заказ в обработке
- `IN_DELIVERY` — Заказ в пути
- `READY_FOR_PICKUP` — Готов к выдаче
- `DONE` — Заказ выдан
- `CANCELED` — Заказ отменён
